# Состояние проекта — 27.09.2026

Рабочая версия: HEAD a8e2fff плюс незакоммиченные пользовательские изменения и исправления.
Целевая нагрузка — до 10 одновременных пользователей. Архитектура осталась modular monolith.

## Что исправлено

- Вехи: миграция 0006, нулевая длительность, CSV, равные фактические даты завершённой вехи.
- Выравнивание ресурсов: backend пересчитывает суммарную нагрузку после каждого переноса;
  граф и факты сохраняются, неустранённые перегрузки показаны явно. Максимум 32 шага,
  глобальная оптимальность не заявляется, сохранение предложения остаётся явным действием.
- Защита от устаревших ответов симуляции, сценария, baseline и выравнивания.
  Правки, сделанные во время сохранения, остаются новым черновиком; ответ их не затирает.
- Восстановление локальной копии с проверкой версии и серверной валидацией перед применением.
  Копия неизвестной/устаревшей версии доступна для JSON-экспорта без автоматической замены.
- Baseline рассчитывается из актуального черновика и сохраняется обычным применением.
- Прогноз с просроченными незавершёнными задачами помечается устаревшим в UI, отчёте и
  AI-контексте. По решению пользователя даты автоматически не сдвигаются; требуется
  уточнить длительности/факты. Неизвестный резерв не выдаётся за наличие запаса.
- Ошибки LLM не маскируются шаблонными советами. Они отображаются как ошибки и не идут
  в историю контекста следующего запроса. Клиент провайдера закрывается, ошибки имеют
  диагностический ID; ключи и тексты провайдера не выводятся в журнал.
- Frontend ограничивает ожидание ответа 60 секундами, не повторяет записи автоматически.
- Календарь хранит числовую сетку UTC вместо сотен тысяч объектов datetime.
- Расчёт проходит вне транзакционной блокировки; перед сохранением версия проверяется
  повторно под блокировкой. Согласованное чтение агрегата защищено разделяемой блокировкой.
- Два расчётных запроса обрабатываются одновременно, до 3 секунд ожидания места,
  затем явная 503. AI-обработчики не блокируют основной цикл FastAPI.
- Caddy перезаписывает адрес клиента для лимита входа; API доверяет ему только в Compose
  за закрытым портом. Logout отзывает токен. Перезапуск единственного worker завершает
  все сессии. PostgreSQL имеет тайм-ауты подключения, блокировки и запроса.

## Проверки

- 35 backend-тестов с настоящей изолированной PostgreSQL, без пропусков.
- 12 frontend-тестов: CSV, даты, восстановление, актуальность ответа, тайм-ауты и ошибки API.
- TypeScript и production-сборка проходят; предупреждение о размере JS bundle остаётся.
- Проверены миграция существующей схемы до 0006 и повторный upgrade head.
- Два одновременных сохранения одной версии: одно успешно, второе получает 409;
  новая версия и история не теряются, блокировка не удерживается во время расчёта.
- В браузере: вход, демопроект с вехой, новая задача в черновике, повторное открытие,
  восстановление через сервер, запись версии 2, фиксация baseline и запись версии 3.
  Отдельный анализ и чат без ключа показали явную ошибку вместо выдуманного ответа.
- 10 одновременных GET демопроекта: все HTTP 200, максимум 1,703 с.
- 10 одновременных симуляций демопроекта: все HTTP 200, максимум 3,039 с.
- Контрольный расчёт пяти различных календарей: 0,807 с против 7,286 с при аудите.
  381120 минут стандартного календаря занимают около 2,91 MiB в массиве вместо
  20,35 MiB списка и datetime-объектов. Это локальные измерения, не характеристики VPS.

## Что требуется при запуске

Рабочая БД пользователя не изменялась. Применить alembic upgrade head с её DATABASE_URL,
затем перезапустить backend и frontend. При локальном запуске API оставить
TRUST_PROXY_HEADERS выключенным; в Compose API не публикует порт наружу.

Внешняя LLM и целевой VPS не проверялись. Prompt не гарантирует отсутствие галлюцинаций;
AI не изменяет план, математические результаты остаются в движке. Перед публикацией
проверить провайдера, HTTPS, резервное копирование и нагрузку на выбранном сервере.
