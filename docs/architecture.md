# Critix: архитектура и границы реализации

Актуализировано по состоянию кодовой базы на 30.09.2026.
Команды запуска — в [operations.md](operations.md), результаты проверок — в [current-state.md](current-state.md), отчет безопасности — в [technical-audit-2026-09-30.md](technical-audit-2026-09-30.md).

```text
React 19 + TypeScript + Vite + Mantine + React Flow
                       │  HTTP/REST (Cookie HttpOnly, X-Critix-Request)
                       ▼
FastAPI (Uvicorn)
  ├── Auth & Rate Limiter (Session Gen, AI Quota Manager)
  ├── Service Layer (owner_id scoping, Aggregate Locks, Drafts)
  ├── Analysis Engine (Pure Python, Deterministic CPM & Calendar Grid)
  │     └── SQLAlchemy 2.0 ──► PostgreSQL 17
  └── AI Copilot (Async HTTP Client, 15s timeout, No DB locks)
```

## 1. Данные, транзакции и изоляция

- **Многопользовательская изоляция:**
  - Каждый проект строго привязан к `owner_id`.
  - Все проектные запросы через `get_current_project` валидируют права владения в рамках сессии БД. Попытка запроса чужого проекта возвращает HTTP 404.
  - Административный вход по `ADMIN_PASSWORD` видит только системные проекты без владельца (`owner_id IS NULL`).
  - Публичный демо-вход отключён (HTTP 410 Gone); авторизованный пользователь может сгенерировать демо-проект в собственный профиль.
- **Целостность агрегата проекта:**
  - Редактирование сохраняет весь агрегат проекта (задачи, связи, исполнители, календари) целиком в одной транзакции.
  - Составные внешние ключи исключают случайные связи между задачами разных проектов.
  - Для чтения согласованного снимка используется разделяемая блокировка. Расчёт CPM выполняется в памяти без удержания блокировки таблицы.
  - Перед записью сервер берёт эксклюзивную блокировку строки (`FOR UPDATE`), повторно проверяет версию и сохраняет новый снимок.
  - При несовпадении версий сервер возвращает HTTP 409 Conflict.

## 2. Математический движок и границы вычислений

- **Топологическая сортировка и DAG:**
  - Проверка ацикличности графа выполняется алгоритмом Кана со сложностью O(V + E). Обнаружение цикла возвращает HTTP 422 до записи в базу.
- **Типы связей и расчет дат:**
  - Поддерживаются 4 типа зависимостей: Finish-to-Start (FS), Start-to-Start (SS), Finish-to-Finish (FF), Start-to-Finish (SF).
  - Лаги могут быть положительными или отрицательными, в рабочих минутах или календарных днях.
  - Прямой проход вычисляет ранние даты (Early Start, Early Finish).
  - Обратный проход вычисляет поздние даты (Late Start, Late Finish) через монотонный поиск по календарной сетке.
  - Полный резерв времени (`slack_minutes`) рассчитывается относительно прогнозного финиша проекта (не целевого дедлайна). Фиксированные фактические даты имеют `slack = None`.
- **Лимиты вычислительного движка:**
  - Максимум 200 задач, 2000 связей, 100 исполнителей на проект.
  - Максимальный горизонт проекта — 1096 дней (~3 года).
  - Суммарный бюджет минутной сетки — 4 млн минут (~32 МБ сырых значений).
  - Бюджет ресурсных интервалов — до 20 000 сегментов на анализ.
  - Кооперативный таймаут вычислений — 10 секунд.
  - Два одновременных расчётных слота (`calculation_slots`), ожидание в очереди до 3 секунд, затем возврат HTTP 503.

## 3. Сценарное моделирование (What-If)

- Пользователь может создать до 20 изолированных сценариев на проект.
- **Оптимизация On-Demand:**
  - Запрос списка сценариев (`GET /api/projects/{id}/scenarios`) возвращает метаданные сценариев **без** пересчёта расписания движком (`include_analysis=False`).
  - Полный расчет сценария (`POST /api/projects/{id}/scenarios/{scenario_id}/analyze`) инициируется пользователем по требованию.
- Применение сценария к основному проекту требует предварительного успешного расчета на актуальной версии базового плана.

## 4. Архитектура интеграции с ИИ (AI Copilot)

- ИИ выполняет исключительно консультационную функцию (Senior PM Copilot) и **не имеет прав на изменение дат или структуры графа**.
- **Разделение ресурсов:**
  - Все факты передаются в LLM в виде готового структурированного JSON-дампа.
  - Сессия базы данных PostgreSQL закрывается **до** отправки сетевого запроса к модели.
  - Подготовка контекста выполняется в пуле потоков через `run_in_threadpool`, освобождая CPU-семафор расчёта до начала сетевого ожидания.
  - Таймаут клиентского вызова LLM — 15 секунд.
- **Управление расходами и квоты:**
  - `AI_DAILY_BUDGET=500` запросов в сутки на инстанс.
  - 50 запросов в сутки на пользователя.
  - Rate-limit: 10 запросов в минуту на пользователя.
  - При недоступности провайдера или исчерпании квоты интерфейс отображает детерминированный отчёт движка (`source: "engine"`).

## 5. Клиентская архитектура и защита данных

- **Защита от перезаписи черновика (DraftBanner):**
  - Локальные изменения непрерывно сохраняются в `localStorage` браузера.
  - При конфликте версий (HTTP 409) или расхождении серверного снимка черновик пользователя не стирается.
  - UI показывает `DraftBanner` с детализированным списком изменений между локальным состоянием и сервером (`computeProjectDiff`), предлагая выбор: принять серверную версию или сохранить поверх.
- **Защита от запоздалых ответов (Stale Async Responses):**
  - Механизм поколений `authGen` и `sessionGen` в контекстах React гарантирует, что медленные сетевые ответы игнорируются, если пользователь успел сменить проект или выйти из учётной записи.
- **Синхронизация схем:**
  - Форматы валидации JSON/CSV на фронтенде строго соответствуют лимитам бэкенда (200 задач, 2000 зависимостей, 100 исполнителей с сохранением ролей и навыков).
