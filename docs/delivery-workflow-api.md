# Поставки подрядчиков и решения по выпуску

Backend управляет обещанным результатом, приёмкой и последствиями для выпуска.
Рабочий день сотрудников подрядчика не моделируется. UI не изменён.

## Воспроизводимый пример

Из каталога backend: `python -m app.delivery_walkthrough --output ../output/delivery-demo`.
В walkthrough.md — объяснение результата, в results.json — полный расчёт.
При фиксированном моменте 1 октября 2026 перенос API с 5 на 6 октября сдвигает
запуск с 9 на 12 октября. Перенос необязательного отчёта в следующий выпуск
сохраняет запуск 9 октября. При доработке без новой даты прогноз неизвестен.
Это учебные данные и реальные вычисления движка.

## Данные проекта

`deliveries` содержит id, name, contractor, promised_at (исходное обещание),
expected_at (текущий прогноз или null), review_days (0–30 календарных дней),
status, delivered_at, accepted_at, dependent_task_ids.
Все даты имеют часовой пояс и точность до минуты. События не меняют promised_at.
Плановое время приёмки — явно указанное допущение, не факт принятия результата.

`optional_task_ids` явно обозначает необязательные работы;
`deferred_task_ids` исключает их из расчёта текущего выпуска, сохраняя в проекте.
Нельзя исключить начатую работу или обязательного предшественника обычной работы.
Нулевые вехи могут объединять обязательные и исключённые ветки.

## Действия и переходы

| Состояние | Доступные события | Результат |
| --- | --- | --- |
| waiting | delay, submit | изменение прогноза / delivered |
| delivered | reject, accept | rework / accepted |
| rework | delay, submit | изменение прогноза / delivered |
| accepted | нет | результат принят |

Фактическое начало любой зависимой работы возможно только после accepted_at.
Ограничение проверяется также при обычном сохранении проекта.

## API для подключения

Все маршруты требуют авторизации и доступа к проекту. Записывающие запросы
используют существующую защиту `X-Critix-Request: 1`.

- `POST /api/demo/deliveries` создаёт отдельный принадлежащий пользователю демопроект.
  Даты адаптируются к текущему моменту; существующие проекты не перезаписываются.
- `GET /api/projects/{id}/delivery-cases` возвращает version и допустимые действия
  для каждой поставки, названия и признаки запроса новой даты.
- `POST /api/projects/{id}/delivery-events/preview` вычисляет последствия без сохранения.
- `POST /api/projects/{id}/delivery-events` применяет событие и выбранное решение.
- `GET /api/projects/{id}/history` включает структурированное поле decision.

Тело предпросмотра (дата — пример, должна соответствовать вашему проекту):

```json
{
  "version": 1,
  "delivery_id": "payment-api",
  "kind": "delay",
  "expected_at": "2026-10-06T09:00:00+05:00",
  "reason": "Подрядчик подтвердил перенос"
}
```

`occurred_at` необязателен: по умолчанию текущий момент. Факты из будущего запрещены.
Для delay/reject `expected_at: null` означает неизвестную дату; для submit/accept
это поле не передают. Причина обязательна и не может состоять из пробелов.

Ответ содержит before, event, variants и requires_confirmation.
Каждый вариант содержит project, analysis и impact: сроки до/после,
сдвинутые работы, цепочки причин, исключённый объём, допущения.
`accept_change` сохраняет полный текущий объём; `defer_optional` предлагается
для delay/reject, если допустимо исключить все ещё не исключённые необязательные работы.
Произвольный выбор подмножества пока не реализован.

При применении к телу добавляются:

```json
{
  "decision": "defer_optional",
  "decision_owner": "Владелец продукта"
}
```

Сохраняются событие, причина, выбор, указанный ответственный, реальный пользователь
и последствия. `external_approval_verified: false`: имя ответственного не является
подтверждением согласования с заказчиком. Изменение и история атомарны;
версия повторно проверяется под блокировкой. При 409 нужно обновить проект
и повторить предпросмотр. Сервер пересчитывает результат при применении.

## Неизвестность и совместимость

Для срока выпуска используйте `analysis.forecast_finish` или `impact.finish_after`.
При неизвестной дате они null, `forecast_complete: false`, а affected-задачи
не получают достоверный запас времени или признак критичности.
`forecast_conditional: true` означает зависимость от ещё не принятой поставки.
Просроченное ожидание без фактической приёмки также делает прогноз неизвестным.
Старое числовое `analysis.finish` сохранено для совместимости и в этих случаях
не должно отображаться как подтверждённый прогноз. Старый UI сам по себе
не показывает новый процесс: требуется подключение перечисленных полей и маршрутов.

Обычный PUT сохраняет серверные deliveries и поля объёма, если старый клиент их
не передал. Явный пустой массив означает намеренное очищение поля.

JSON-поля поставок/объёма в projects и решения в changes.
