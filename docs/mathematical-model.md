# Математическая модель Critix

Реализация: `backend/app/engine/analysis.py` и `calendar.py`.
Все величины расписания вычисляются Python. AI не является расчётным модулем,
не изменяет проект и не подтверждает эффект гипотез без вызова симуляции пользователем.

## Вход и календарь

Проект — ориентированный ациклический граф G=(V,E). Вершина i — задача с длительностью
d_i в целых рабочих минутах. Циклы отвергаются топологической сортировкой Кана.
Загрузка a_i в процентах — отдельный параметр: 50% не удваивает d_i.

Календарь задачи C_i — пересечение рабочего календаря проекта и календаря исполнителя.
Дневные исключения заменяют расписание дня; пустое исключение означает нерабочий день.
Локальные интервалы интерпретируются в IANA-поясе проекта и переводятся в UTC-минуты.
Пусть W_i[k] — k-я доступная рабочая минута в возрастающем порядке.

S_i(k)=W_i[k], F_i(k)=W_i[k+d_i−1]+1 минута.
Это учитывает выходные, перерывы, отпуска и смену часового смещения.
Нахождение ближайшего доступного индекса выполняется двоичным поиском.

## Ограничения зависимостей

Для ребра i→j обозначим L_ij(t) сдвиг момента t на заданный lag.
В календарном режиме это t+lag минут; в рабочем режиме используются слоты C_j.
Нулевой lag оставляет момент неизменным; отрицательный разрешает опережение.

| Тип | Ограничение |
|---|---|
| FS | S_j ≥ L_ij(F_i) |
| SS | S_j ≥ L_ij(S_i) |
| FF | F_j ≥ L_ij(F_i) |
| SF | F_j ≥ L_ij(S_i) |

Также S_j ≥ max(старт проекта, not_before_j). При нескольких входящих связях
берётся максимум нижних границ. Для FF/SF поиск минимального допустимого индекса
начала учитывает ограничение окончания. Фактическое начало фиксировано; у завершённой
задачи фиксировано и окончание. Несовместимость фактов с ограничениями даёт флаг конфликта,
а не незаметное перемещение фактических дат.

## Прямой и обратный проход

Прямой проход по топологическому порядку выбирает самый ранний допустимый индекс k_i.
Прогноз завершения T=max_i F_i. Целевой дедлайн D не заменяется прогнозом T.
Превышение дедлайна: max(0, (T−D) в календарных минутах).

Обратный проход идёт от последователей к предшественникам. Ищется максимальный индекс
k_i^late, при котором F_i ≤ T и все исходящие ограничения соблюдаются относительно
уже вычисленных поздних дат последователей. Проверка допустимости монотонна; используется
двоичный поиск. Вычитать lag из даты напрямую нельзя из-за разных рабочих календарей.

Резерв slack_i=k_i^late−k_i выражен рабочими минутами календаря задачи.
Это резерв относительно T, а не относительно D. Нулевой резерв означает критическую
задачу. Для фиксированных фактических дат резерв не вычисляется (`null`).
Критических ветвей может быть несколько. Связь попадает в `critical_dependencies`,
если оба конца критические и сдвиг предшественника на одну рабочую минуту нарушает
ограничение ранней даты последователя. UI использует именно этот результат.

## Загрузка, риски, сценарии

На каждом рабочем интервале исполнителя суммируются a_i активных незавершённых задач.
Сумма >100% образует период перегрузки. Границы интервалов обрабатываются методом событий.
Это обнаружение конфликтов ресурсов, а не автоматическое выравнивание расписания.

Флаги: blocked — введённая блокировка; dependency_conflict — нарушение временного
ограничения; past_deadline — окончание задачи после D; overload — участие в перегрузке;
overdue — задача не завершена и F_i раньше контрольного момента as_of.
При фиксированных проекте и as_of результат воспроизводим. Просрочка не меняет
расписание автоматически: факты или длительность должен уточнить руководитель.

Симуляция использует тот же analyze(), но не записывает новый план.
ΔT=(T_сценария−T_сохранённого) в календарных минутах; сравнение включает изменения
других полей текущего черновика. Изменившиеся задачи — те, у которых поменялись даты.
Downstream — достижимые потомки изменённых задач/связей; достижимость сама по себе
не означает фактического сдвига даты. Отклонение от baseline считается отдельно:
(T−T_baseline) в календарных минутах, без предположения о восьмичасовом дне.

## Пример и проверка

При едином календаре 09:00–13:00, 14:00–18:00 и двух задачах по 480 минут,
связанных FS с нулевым lag, первая занимает понедельник, вторая — вторник.
Независимая задача на 60 минут имеет резерв 900 рабочих минут относительно финиша
во вторник в 18:00. Добавление первой задаче 480 минут переносит финиш цепочки
на среду в 18:00. Этот пример проверяется в `test_cascade_slack_and_deadline`.

Другие тесты покрывают четыре типа связей, lag, циклы, календари, фактические даты,
перегрузки и симуляцию. Тесты — проверка выбранных случаев, не формальное доказательство
корректности для всех возможных входов.

## Границы модели

Горизонт сетки: старт минус 370 дней — старт плюс 740 дней. Проект ограничен одним годом,
200 задачами, 2000 связями и 100 исполнителями. Топологическая сортировка O(V+E);
поминутная сетка определяет основную стоимость памяти. Модель не оценивает вероятность
срыва, бюджет, скорость обучения или ускорение от найма. Конфликтные фактические данные
помечаются; при таких флагах расписание нельзя называть полностью допустимым.
