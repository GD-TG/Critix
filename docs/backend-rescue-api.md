# Backend: расчёт последствий и проверка решений

Изменения ограничены backend и этой документацией. Существующие поля API сохранены;
новые поля и endpoints можно подключать на frontend постепенно.

## Развёртывание

Перед запуском новой версии выполнить `alembic upgrade head` из `backend`.
Dockerfile уже выполняет миграции перед стартом API. Миграция `0009` добавляет
nullable `tasks.remaining_minutes` и ограничение допустимых значений.
Существующие задачи получают NULL и продолжают рассчитываться по прежней длительности.

## Создание и сохранение задач

Существующий контракт остаётся: `POST /api/projects/{id}/simulate` и
`PUT /api/projects/{id}` принимают `{version, project, comment?}`.
Чтобы добавить задачу, включить её и связи в полный `project`.
Симуляция не сохраняет данные; PUT атомарно сохраняет агрегат, увеличивает версию
и добавляет запись истории. Пустые и состоящие из пробелов названия отклоняются
с 422; внешние пробелы названий удаляются. При 409 нужно получить актуальную версию.
Требуются сессия, разрешённый Origin и заголовок `X-Critix-Request: 1`.

Backend не может исправить кнопку, которая не отправляет запрос. Сообщение
«Сохранено» в интерфейсе должно появляться после успешного PUT.

## Остаток работы и критичность

Новый необязательный атрибут задачи: `remaining_minutes: integer | null`, 0…525600.
Допустим только при `actual_start` и статусе `in_progress` или `blocked`.
Это явная оценка оставшихся рабочих минут **на момент текущего расчёта** (`analysis.as_of`).
Движок не вычитает автоматически прошедшее календарное время из оценки.
Если план используется позднее, оценку необходимо подтвердить/обновить; без этого
результат условен относительно предположения, что указанный остаток всё ещё актуален.

Фактический старт сохраняется. Остаток размещается не раньше `as_of`, фактического
старта и `not_before` в пересечении календарей проекта и исполнителя. Время округляется
вверх до минуты. FF/SF-ограничения на финиш учитываются. `not_before` по-прежнему
является ограничением старта: противоречащий ему фактический старт отмечается конфликтом.
При завершении задачи очистить `remaining_minutes` и указать фактический финиш.

Для текущей начатой задачи рассчитывается резерв задержки её окончания, фактический
старт не передвигается. Для просроченной начатой задачи без оценки остатка резерв
неизвестен: `criticality_known=false`, `slack_minutes=null`, `forecast_stale=true`.
Для выполненной задачи резерв не применяется. `latest_finish` добавлен к строкам анализа.
Критичность при устаревшем прогнозе нельзя трактовать как актуальную гарантию.

Статус `blocked` означает риск, а не заданную длительность задержки. До уточнения
ожидаемого возобновления расчётные даты остаются условными.

## Анализ и последствия

`analysis` содержит:

- `snapshot_id`: SHA-256 входного проекта и `as_of`; один и тот же ввод и момент дают один ID.
- `as_of`: UTC-момент расчёта. До/после и варианты сравниваются в один момент.
- `health`: `empty | ok | attention | intervention | stale`.
- `intervention_required`: есть предупреждения высокой важности.
- `attention`: упорядоченные записи `{id, severity, code, task_ids, reason, action}`.

Предупреждения высокой важности: устаревший прогноз, нарушение дедлайна, блокировка,
конфликт зависимостей и просрочка. Средней: нулевой резерв и перегрузка.
Ручной приоритет задачи используется для порядка внутри важности; он не заменяет CPM.

Дополнительные поля `changes`:

| Поле | Значение |
| --- | --- |
| `changed_task_ids` / `date_changed_task_ids` | Новые задачи или задачи с изменением старта/финиша; прежняя семантика сохранена |
| `edited_task_ids` | Задачи с изменёнными входными полями, включая добавление/удаление |
| `calculation_root_task_ids` | Корни влияния, включая изменения календарей, исполнителей и связей |
| `risk_changed_task_ids` | Изменились флаги риска, критичность или резерв |
| `critical_added_task_ids`, `critical_removed_task_ids` | Изменение состава критических задач |
| `downstream_task_ids` | Потенциально затронутые потомки; не утверждает, что все их даты изменились |
| `new_alerts`, `resolved_alert_ids` | Новые и исчезнувшие предупреждения по стабильным ID |
| `delay_before_minutes`, `delay_after_minutes` | Превышение дедлайна в календарных минутах |

`finish_delta_minutes` также выражен в календарных минутах. Рабочие длительности
и календарный сдвиг нельзя делить на один и тот же «рабочий день».

## Проверка решений

`POST /api/projects/{id}/recommendations`

```json
{
  "version": 3,
  "project": "полный объект ProjectInput",
  "alternatives": ["до трёх полных альтернативных ProjectInput"],
  "include_leveling": true
}
```

Строки в примере — обозначения объектов, не буквальное тело запроса.
`project` — выбранный пользователем исходный план/черновик; альтернативы сравниваются
именно с ним. Версия проекта проверяется до и после расчёта, чужой проект возвращает 404.

Ответ: `{id, version, source: "engine", analysis, proposals, actions, limited, units, limitations}`.
При перегрузках движок может предложить существующее ресурсное выравнивание;
остальные варианты задаёт пользователь. Сроки, производительность и навыки не выдумываются.
Варианты, меняющие фактические даты или удаляющие выполненную работу, отклоняются.

Проверенное предложение содержит `verified=true`, `project`, `analysis`, `changes`,
`finish_gain_minutes` (положительное — раньше, отрицательное — позже),
`overload_before_minutes`, `overload_after_minutes`, `new_high_alerts`,
`assumptions`, `requires_review=true`.
Метрика перегрузки — сумма календарных минут интервалов × превышение загрузки / 100:
200% в течение часа дают 60 минут избыточной загрузки.
`verified` означает успешный расчёт, а не гарантию реализуемости решения.
Недопустимый вариант содержит `verified=false` и `error`. `limited=true` сообщает
об исчерпании общего бюджета вычислений; необработанные варианты не выдаются за проверенные.

Никаких изменений в БД этот endpoint не делает. Для применения выбранного
`proposal.project` использовать существующий PUT с актуальной версией.
Отличие Critix — проверка решений на производственных календарях, четырёх типах
связей, фактических датах и ресурсной загрузке, с явным описанием цены решения.

## Copilot и диагностика

Для внешнего AI нужно явно задать все три переменные: `LLM_API_KEY`, `LLM_MODEL`,
`LLM_BASE_URL`. Пустые значения переводят ответ в расчётный режим с конкретным
`reason`. Автоматического выбора другого провайдера или модели нет.
`GET /api/ai/status` (с авторизацией) возвращает `configured`, `reason`,
`provider_verified=false`, `fallback_available=true`. Это проверка настройки,
не платный запрос и не доказательство доступности провайдера.

Состав данных, отправляемых внешнему провайдеру, не расширен.
`POST /chat` по-прежнему принимает историю и необязательный `project`; добавлен
необязательный `version`. Устаревшая указанная версия даёт 409. Без `project` чат
работает по сохранённому плану, с ним — по переданному черновику.

Ответы `/ai` и `/chat` дополнены `context: {version, scope, snapshot_id, as_of}`.
Клиент должен сопоставлять ответ с запросом и не показывать его как актуальный
после изменения черновика. `scope` — `saved` или `draft`.

Сохраняются `available` и `text`/`reply`. `source: "llm" | "engine"` указывает источник.
Резервный ответ содержит `reason`: отсутствие настройки, ошибка/пустой ответ
провайдера, `queue_timeout` или `provider_timeout`. Очередь ограничена 1 секундой,
ожидание ответа — 16 секундами, сетевой timeout клиента — 12 секундами, retry отключён.
При отказе используется локальная сводка с конкретными предупреждениями и действиями.
Ошибка авторизации, невалидный проект, перегрузка расчётного ядра или квота по-прежнему
возвращают соответствующий HTTP-код; они не маскируются фиктивным успехом.

## Сценарии и проверка

Количество сценариев проверяется повторно под блокировкой проекта перед вставкой.
Список сценариев проверяет целостность графа даже без дорогого календарного расчёта.
Повреждённый сценарий возвращается с ошибкой и остаётся удаляемым. Расчёт списка
использует общий бюджет и расчётный семафор. Снимок основного плана читается
под одной блокировкой; сессия освобождается до расчёта отдельного сценария.

Регрессии: `backend/tests/test_backend_rescue.py`, `test_rescue_postgres.py`,
существующие engine/AI/auth/migration/concurrency тесты. Изолированный полный прогон:

```powershell
docker compose -p critix-backend-rescue-tests -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from test
```
