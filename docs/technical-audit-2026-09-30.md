## 1. Top-10 проблем перед хакатоном

Порядок учитывает и работоспособность демонстрации, и возможность открытия сервиса посторонним. Если публичного сервера пока нет, A05 не мешает локальному показу, но остаётся обязательным перед публикацией.

1. **A01 — ограничить вычислительные ресурсы.** Один валидный запрос не должен иметь возможность потребовать гигабайты памяти.
2. **A02 — закрыть бесконечное создание demo-данных.** Иначе любой посетитель обходит расчётный лимитер и расходует БД.
3. **A03 — устранить подмену IP лимитера.** Доказан обход через реально запущенный Caddy.
4. **A04 — ограничить платный AI.** Demo не должен превращать ключ сервиса в общедоступный источник расходов.
5. **A05 — настроить публичный HTTPS.** Только после этого публиковать вход с реальными паролями.
6. **A07 — сохранить черновик при refresh/смене проекта.** Это прямой риск потери пользовательской работы.
7. **A08 — исправить дату новой начатой задачи.** Поломка обычного пути без злоумышленника.
8. **A09 + A10 — валидировать импорт и восстановить аварийный экран.** Некорректный JSON не должен уничтожать рабочее пространство.
9. **A11 + A12 — связать ответы с проектом и сессией.** Поздние ответы не должны заменять актуальный выбор пользователя.
10. **A06 — освободить авторизационное соединение до LLM.** Проверять это полным API-вызовом на PostgreSQL.

Следующий пакет по математике: A13–A17 и A22. Они обязательны для заявлений о корректности произвольных календарей/фактических дат, даже если не входят в один заранее подготовленный демо-проект.

## 2. Security

### Подтверждённые проблемы и границы эксплуатации

- **DoS вычислениями:** A01. Достаточно собственного аккаунта; demo выдаёт его публично. Большие массивы намеренно не выделялись.
- **Анонимное истощение ресурсов и диска:** A02. Нет ограничения demo и времени хранения созданных данных.
- **Обход защиты входа/регистрации:** A03. Воспроизведён через proxy, а не только прямым вызовом функции.
- **Неограниченный расход LLM:** A04, A23. Платную эксплуатацию не выполнял.
- **Публичный HTTPS:** A05. Локальный CA пригоден для управляемого локального окружения, но не для произвольных посетителей.
- **Избыточные права БД:** A33. Усилитель последствий другой компрометации, не доказанная точка входа.
- **CSV-formula injection:** A24. Требуется открытие экспортированного файла в редакторе, выполняющем формулы; межпользовательский обмен проектами не предполагается автоматически.
- **Остаточные данные клиента после смены сессии:** A12. Серверные проверки ownership остаются действующими.

### Что проверка не подтвердила как уязвимость

- **Старый IDOR не воспроизведён:** load фильтрует владельца; scoped session применяется к проектным маршрутам, owner передаётся в подготовку AI. Проекты без owner не выдаются обычным пользователям. Проверены account-isolation тесты.
- **Чужие task_id/assignee_id:** схема проверяет принадлежность агрегату, а составные FK связывают задачи/сотрудников с project_id. Одинаковый task_id в разных проектах не означает общую задачу.
- **Mass assignment:** ProjectInput/SaveProject запрещают лишние поля, owner_id берётся из сессии. Передача user_id в проекте не назначает владельца.
- **SQL injection/command injection:** в изученных путях пользовательские значения не подставляются в SQL/командную строку; ORM-параметры и фиксированный SQL healthcheck. Поиском не найден эксплуатируемый путь.
- **SSRF/path traversal:** LLM_BASE_URL задаёт оператор, а не пользователь API; пользовательского fetch URL и серверного сохранения импортируемых файлов по имени не найдено.
- **XSS:** React и используемый Markdown-рендер не создают подтверждённого пути исполнения пользовательского HTML. Это не освобождает от проверки при будущем добавлении HTML/ссылок/плагинов.
- **CSRF:** изменяющим запросам нужен нестандартный header; Origin проверяется при наличии, cookie SameSite=Strict. Отсутствие Origin у небраузерного клиента не обходит авторизацию и не является само по себе CSRF.
- **Секреты в клиентском bundle:** источников включения LLM_API_KEY в frontend не найдено. Ключи не выводились в отчёт.
- **Stack trace клиенту:** общий обработчик 500 его скрывает; проблема обратная — недостаточно подробный серверный лог A36.

Дополнительное усиление после срочных правок: регистрация допускает пароль от шести символов; стоит усилить политику и защиту по аккаунту. В verify_password есть fallback сравнения с открытой строкой при неизвестном формате хеша — для обычных регистраций используются PBKDF2-хеши, путь подмены hashed_password через API не найден. Удалить fallback после проверки совместимости, но не выдавать его за подтверждённый захват аккаунта.

Cookie — подписанный HMAC-токен, не JWT. boot_key процесса намеренно отзывает сессии после рестарта. При добавлении нескольких workers возникнет несовместимость сессий между процессами; текущая конфигурация запускает один worker, поэтому это ограничение архитектуры, а не текущий баг многопроцессного запуска.

## 3. Основной пользовательский сценарий

**Ответ: стандартный путь проходит, но устойчивость к обычным отклонениям недостаточна.** Это подтверждают интеграционные тесты HTTP и отдельный чистый запуск; полный клик-за-кликом browser E2E в этом аудите не выполнялся.

| Этап | Текущее поведение | Где ломается |
|---|---|---|
| Создать проект | Сервер проверяет схему, рассчитывает и сохраняет агрегат | POST успешен, следующий GET списка падает — UI не принимает созданный проект, A28 |
| Создать задачи | Обычные todo-задачи поддерживаются, есть вехи и фактические даты | Новая in_progress — дата с секундами, A08; неправильный импорт — A09/A25 |
| Задать зависимости | FS/SS/FF/SF, working/elapsed lag, проверка циклов и ссылок | Часть допустимых больших lag/поздних ограничений не покрывается горизонтом, A13 |
| Изменить задачу | Черновик отделён от saved; simulate не коммитит | Refresh/переключение теряет черновик, A07; поздний ответ другого проекта — A11 |
| Рассчитать последствия | Детерминированный engine, проверка версии до/после анализа | A01, A13–A16; неполное описание downstream при изменении календаря/начала A17 |
| Показать результат | Возвращаются dates/slack/critical/risk flags/изменения; AI отдельно | Противоречивая сводка A22, падение recovery A10; обычная задача отсутствует в чат-контексте A21 |
| Сохранить | Row lock + повторная проверка версии; конфликт даёт 409 | Поведение при конфликте защищено текущими тестами. При обрыве ответа исход сохранения остаётся неопределённым до повторного чтения — UI об этом предупреждает |

Цикл в сценарии теперь анализируется **до commit**. Неудачный пересчёт при применении сценария не должен заменять draft старой аналитикой: текущие regression-тесты это подтверждают. История уже описывает изменения календаря, команды и зависимостей; прежнее замечание о сравнении только задач повторно не выставляется.

## 6. Тесты, которые нужно добавить

### P0 — дорогостоящие ошибки и границы безопасности

1. **Бюджет расчёта:** 200×max duration, много различных календарей и крайние actual/not_before. Проверять отказ до WorkCalendar, без настоящего OOM.
2. **Demo-limiter:** burst получает 429; число записей и расходов ограничено; TTL удаляет только demo-данные.
3. **Proxy-limiter через Caddy:** подмена X-Critix-Client-IP не меняет идентичность клиента; отдельный тест лимита по аккаунту.
4. **AI-квота:** demo/обычный пользователь, параллельные запросы, отказ провайдера. Ни одно отклонение квоты не вызывает LLM.
5. **Полный AI API lifecycle:** реальная Depends(current_user), PostgreSQL, задержанный fake-provider; соединение и транзакция не остаются занятыми во время ожидания.
6. **Новая in_progress-задача через UI:** ввод → статус → сохранение карточки → simulate → save → reload; точность всех дат до минуты.
7. **Черновик:** refresh, смена проекта, logout/login другого пользователя, конфликт серверной версии при восстановлении. Нельзя восстановить черновик одного владельца в сессию другого.
8. **Импорт:** tasks=[null], несуществующая timezone, неверные типы навыков/календарей, 201 задача, слишком длинные строки. Старый draft остаётся целым.
9. **ErrorBoundary:** намеренная ошибка рендера поднимает рабочий fallback, не вызывает вторую ошибку и сохраняет проектный state.
10. **Порядок ответов:** A→B, задержанный ответ A; logout во время bootstrap; два логина разных аккаунтов. Принимается только актуальное поколение проекта/сессии.

### P1 — математическая корректность

11. Веха до смены/после смены/в выходной: start=finish при duration=0, в том числе actual_start.
12. Только завершённые задачи и пустой календарь; смешанный проект done+todo; календарь нужен только там, где требуется рабочая арифметика.
13. Поздний not_before и положительный/отрицательный working-lag на границе поддерживаемого горизонта: корректный результат либо документированный 422, никогда 500.
14. Крайние годы/часовые смещения: безопасная валидация без OverflowError.
15. Изменение только project.start, календаря проекта и календаря сотрудника: согласованное объяснение изменений/downstream.
16. Ночные смены через полночь, 24-часовая доступность, переход DST: точный подсчёт рабочих минут после согласования модели.
17. Независимая проверка CPM для маленьких случайных DAG: несколько predecessor/successor, disconnected tasks, разные календари, все четыре типа связей и lag. Сравнивать с простым перебором допустимых стартов на малой сетке, а не с копией production-алгоритма.
18. Для calculated-task с ненулевым slack: сдвиг в пределах slack не нарушает ограничений и finish; на следующую рабочую минуту проверять ограничивающее условие. Для actual-started задач отдельно документировать `slack=null`, не превращать его в нулевой/бесконечный запас.
19. Одна задача, пустой проект, равные границы вехи, отрицательная длительность, самоссылка, цикл, дубли ID. Проверять не только анализ, но и отсутствие невалидной записи после отказа API.
20. Детерминированный fallback при dependency_conflict, blocked, overload и forecast_stale: ни один конфликтный план не маркируется безусловно безопасным.

### P1 — транзакции и пользовательский поток

21. Отказ создания стартового проекта при регистрации: предсказуемый атомарный результат либо явно подтверждённый аккаунт без demo.
22. Две конкурентные регистрации одного email: один аккаунт, согласованный 4xx второго запроса, отсутствие 500.
23. Успешный POST проекта + ошибка GET списка; потеря ответа POST + повтор: нет скрытого успеха и неожиданных дубликатов.
24. Список сценариев с количеством больше страницы: ограниченный ответ/время, без анализа всех snapshots.
25. Импорт 2 задач в проект с 199, max duration+1, CSV с формульными префиксами и кавычками/Unicode.
26. Основной browser E2E: создать проект → сотрудника → 3 задачи → разветвлённые связи → изменить длительность → preview → save → refresh → проверить даты и историю.
27. Две вкладки: один 409, сохранение локального draft, понятный выбор загрузки/перезаписи, поздний ответ не влияет на другой проект.
28. Чистая PostgreSQL и upgrade существующей БД до head; восстановление из резервной копии. Существующие миграционные тесты сохранить.

### P2 — эксплуатация

29. Десять сессий с небольшими проектами: измерить p50/p95, число 5xx/503, память API и pool wait при сохранениях, сценариях и медленном fake-AI.
30. HTTPS на внешнем домене: валидная цепочка, HTTP-редирект, Secure/HttpOnly/SameSite cookie, корректные Origin и proxy headers.
31. Недоступный localStorage, мобильное меню, ограниченная сеть, повторный клик, удаление уже удалённого объекта и 404 — без белого экрана и скрытых ошибок.
32. Проверка версии API-ответа/не-JSON 200: контролируемая ошибка клиента, сохранённый draft.
